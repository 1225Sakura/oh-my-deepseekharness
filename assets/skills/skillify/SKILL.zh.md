# skillify（技能提炼）

当前会话发现了一个值得固化成可复用 dsh 技能的可重复工作流时，使用本技能。

## 目标

把一次成功的多步工作流捕获为具体的技能草稿，而不是以后重新踩一遍坑才发现它。

## 质量门

提炼技能之前，三条必须全部为真：
- "这东西 Google 五分钟能查到吗？" → 不能。
- "它是否专属这个代码库、项目或工作流？" → 是。
- "它的发现是否付出了真实的调试、设计或运维成本？" → 是。

优先提炼编码了决策启发式、约束、坑与验证步骤的技能。避免通用片段、样板代码、属于普通文档的库用法示例。

## 流程

1. 识别本会话完成的那个可重复任务。
2. 提取：
   - 输入
   - 有序步骤
   - 成功判据
   - 约束 / 坑
   - 验证证据
   - 技能的最佳目标位置
3. 判断该工作流的归宿：
   - 项目技能（`.dsh/skills/<name>/SKILL.md`——可 commit，随仓库与团队共享）
   - 用户技能（`~/.dsh/skills/<name>/SKILL.md`——对该操作者跨全部项目可用）
   - 仅写文档
4. 起草技能文件时，输出一个以 YAML frontmatter 开头的完整 `SKILL.md`。
   - 绝不产出没有 frontmatter 的纯 markdown 技能文件。
   - dsh frontmatter（键名只允许 `[A-Za-z-]`）：
     ```yaml
     ---
     name: <skill-name>
     description: <一行描述>
     when-to-use: <一行，点名应触发本技能的情形>
     ---
     ```
   - dsh 扫描项目根 `.dsh/skills/` 与用户根 `~/.dsh/skills/`；每个技能一个目录，内含 `SKILL.md`（项目双语工作时可选配 `SKILL.zh.md` 中文副本）。
   - 记住：未 commit 的项目技能仍是 worktree 本地的，直到 commit 或复制到用户级目录。
5. 起草技能文件其余部分：清晰的触发条件、步骤、成功判据、坑。为没有聊天记录的读者而写（见 `agent-doc-discipline`）。
6. 指出仍然太模糊、无法安全编码的部分。

## 规则

- 只捕获真正可重复的工作流。
- 技能保持实用、有界。
- 显式成功判据优先于含糊散文。
- 工作流还有未解决的分支决策时，起草前先标注。
- 一个技能一个目录一个 `SKILL.md`；frontmatter 的 `name` 必须与目录名一致。

## 输出

- 提议的技能名
- 目标位置
- 草稿工作流结构或完整技能文件
- 验证或质量门说明
- 悬而未决的问题（若有）

## 状态契约

skillify **不持模式状态**。它不做 `state_write`/`state_clear`；交付物是起草的技能文件。如果会话产出的是不构成技能的耐久知识，改走 `remember` 技能的记忆面，不要硬塞进技能里。

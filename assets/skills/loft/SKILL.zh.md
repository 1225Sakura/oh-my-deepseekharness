# loft（放样）

**线型不光顺，就不切钢。** 造船工在切第一块钢板之前，把船体线型按实尺放样、修顺。loft 把同样的次序用于设计问题：话语用尽时——两个都合理的答案，空谈无法证伪——造一个便宜的可运行工件，让船长对它做出反应，把这个反应折回决策。

**角色契约。** 船员造工件；船长唯一的工作是反应——而这个反应**就是**决策。工件是观察仪器，绝不是交付物的先行偷跑。

## 何时放样

- 设计问题在散文里卡住：反复重述仍无法定夺（"路径页该长什么样"、"这个状态模型手感对不对"）
- 规格讨论走到"得先看到实物"

**不要**放样的情况：

- 问题查仓库证据或问船长就能答（那是访谈，不是放样）
- 目的地本身不清（那是雾——交给 `ask-navigator` 绘制成决策票地图；或用 `deep-interview`/`plan` 先收敛目的地）
- 答案已在 ADR 里（既定决策不重新放样）
- 这个"设计问题"其实是个 bug（那是 `omd-agent-debugger` 的辖区）

## 选分叉

按问题在问什么来选。选错分叉，整个工件白造。

### 逻辑分叉——模型对不对？

关于状态、业务规则、数据形状或算法的问题（"重考时解锁会回归吗？"、"这个 reducer 在边界上成立吗？"）：

1. 把承载决策的核心——状态机、reducer、schema 或算法——隔离成**纯模块**：无 DOM、无 I/O、无框架。写法要求：形状一旦确认，原样搬进真实代码库。
2. 包进一个可点击 HTML 壳：一个场景一个按钮，按顺序走完刁钻边界情况，每次点击后完整状态可见。
3. 确认后模块即可起吊——作为正式工作经 launch 重新进入。放样期间 `main` 不动，壳留在分支上。

### UI 分叉——该长什么样？

关于形状与布置的问题（"步骤条还是卡片？"、"进度放哪？"）：

1. 一个路由，**三个结构不同的变体**——信息架构、导航模型、密度。只有样式差异的变体什么也回答不了：三个换皮是壁纸。
2. 页面上放切换器轮换变体；尽可能嵌进现有产品，让真实数据密度压测设计，而不是三行整齐的假数据。
3. 确认后，**决策**迁移走，变体留在分支上，作为"为什么长这样"的记录。

## 纪律

- 一条命令能跑——用仓库现有最简单的 serve 命令；`file://` 模块 CORS 会咬人就把模块内联进壳。几秒加载；不引入仓库已有之外的构建步骤。
- 无持久化、无测试、无抽象、happy path 之外无错误处理。工件应该是你**不想发布**的东西——这些规则就是为了保住这一点。
- 预期第一个形状会被争辩：在同一会话内于分支上修改。船长确认**最终**形状才是决策；没人争辩的工件通常回答了一个没人有的问题。
- 工件的全部寿命是几分钟建造、一个会话定夺。它一旦开始长成生产代码，停：那是 launch 的活，不是 loft。沉没成本正是本技能要防的失败模式。
- 一次放样回答**一个**问题。两个问题就是两次放样——或者一个其实是两个的问题。

## 折回答案

工件是证据，不是落地。船长反应后：

1. 把决策记在它该住的地方——issue 评论、规格的 Implementation Decisions、或待决笔记——用船长自己的话加一行 why。比散文更精确的片段（reducer、状态机、schema）可内联进去，标注来自放样。
2. 把工件推到 `loft/<name>` 分支。它永不合并：留着，未来读者在意决策的"为什么"时能打开它。
3. 工件的一行代码都不进 `main`——逻辑分叉里确认的模块经 launch 作为正式工作重新进入；UI 分叉里真实页面按决策重新造。

## 范围与非目标

- loft 产**答案，不产交付物**：无运行时、无状态文件、无常驻物。
- 不诊断（`omd-agent-debugger`）、不导航雾气（交给 `ask-navigator`（首选）/`deep-interview`/`plan`（替代））、不自我批准答案（船长的反应是唯一验收）。
- 不替代 seam 批准：放样 UI 展示形状；它的测试 seam 仍在 launch 的 C2 批准。

## 完成定义

船长反应了，答案落在决策该住的地方，工件躺在自己的分支上——工件没有一行进 `main`。

## 状态契约

loft **不持模式状态**：无 `state_write`/`state_clear`，`.omd/` 下不写任何东西。工件活在 `loft/<name>` git 分支上；决策活在决策该活的地方（issue 评论、规格段落、ADR）。中断恢复态就是分支本身——早 push，事后重开。

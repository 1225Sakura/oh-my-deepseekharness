# ai-slop-cleaner（AI 残渣清理）

用本技能清理 AI 生成的代码残渣，不漂移范围、不改变既有行为。在 omd 中，这是面向"能跑但臃肿、重复、测试薄弱、过度抽象"代码的有界清理工作流。它与 `minimal-code-discipline` 互为表里：那个在残渣被写出来之前拦住它，这个在残渣落地后清理它。

## 何时使用

- 用户明确说 `deslop`、`anti-slop` 或 `AI slop`
- 请求是清理或重构感觉嘈杂、重复、过度抽象的代码
- 后续实现留下了重复逻辑、死代码、包装层、边界泄漏或薄弱的回归覆盖
- 用户要一个只评审的 anti-slop 复查（`--review`）
- 目标是化简与清理，不是交付新功能

## 何时不用

- 任务主要是新功能构建或产品改动
- 用户要的是大范围重设计，而不是增量清理
- 请求是泛泛的重构，没有化简或 anti-slop 意图
- 行为模糊到无法用测试或具体验证计划保护

## 执行姿态

- 除非用户显式要求行为变化，否则保持行为不变。
- 可行时先用聚焦的回归测试锁住行为。
- 改代码之前先写清理计划。
- 删除优先于新增。
- 复用现有工具函数与模式，再考虑新写。
- 不引入新依赖，除非用户显式要求。
- diff 保持小巧、可回滚、聚焦坏味道。
- 简洁且证据密集：检查、修改、验证、报告。
- 用户的新指令视为局部范围更新，不丢弃此前不冲突的约束。

## 限定文件清单的用法

当调用方已经知道安全的清理面时，本技能可以被限定在显式文件清单或 changed-file 范围内。

- 好例子：以 `skills/ralph/SKILL.md skills/ai-slop-cleaner/SKILL.md` 为目标调用本技能
- 好例子：ralph 会话只交接该会话改动过的文件
- 即使范围是短短的文件清单，也保持同一套回归安全流程
- 不把 changed-file 范围悄悄扩大成更大的清理工作，除非用户显式要求

## ralph 集成

omd 的 `ralph` 技能可以把本技能作为评审后的有界清理 pass 调用。

- 该工作流中 cleaner 以标准模式运行（不是 `--review`）
- 清理范围仅限 ralph 会话改动的文件
- 清理 pass 之后，ralph 在完成前重跑回归验证
- `--review` 始终是只评审的后续模式，不是 ralph 集成的默认路径

## 评审模式（`--review`）

`--review` 是清理工作起草完成后的只评审 pass，存在的意义是为 anti-slop 工作保住显式的 writer/reviewer 通道分离。

- **Writer pass**：在测试锁住行为的前提下做清理改动。
- **Reviewer pass**：检查清理计划、改动文件与验证证据。
- 同一个 pass 不得既写又自我批准高影响清理——通道分离是 omd 硬规则：高影响清理的评审 pass 必须在独立上下文运行，用 `subagent` spawn `omd-agent-code-reviewer`（先用 `skill` 工具加载角色卡），绝不在作者上下文里自我批准。

评审模式下：
1. **不要**上来就改文件。
2. 评审清理计划、改动文件与回归覆盖。
3. 重点检查：
   - 残留的死代码或未使用的导出
   - 本该合并的重复逻辑
   - 仍在模糊边界的无谓包装或抽象
   - 被保持行为缺失测试或验证薄弱
   - 看似无意改变了行为的清理
4. 产出评审裁决与必须的后续项。
5. 把需要的改动交回独立的 writer pass，不在同一步里既修又批。

## 工作流

1. **先保护当前行为**
   - 明确什么必须保持不变。
   - 改动之前补或跑最窄的回归测试。
   - 测试实在无法先行，就在动代码前显式记录验证计划。

2. **先写清理计划再写代码**
   - 把本次 pass 限定在用户要求的文件或功能区域内。
   - 列出要清除的具体坏味道。
   - 工作从最安全的删除排到风险较高的合并。

3. **编辑前先给残渣分类**
   - **Duplication** —— 重复逻辑、复制粘贴的分支、冗余 helper
   - **Dead code** —— 未使用的代码、不可达分支、过期的 flag、调试残留
   - **Needless abstraction** —— 透传包装、投机性间接层、只用一次的 helper 层
   - **Boundary violations** —— 隐藏耦合、错位的职责、跨错层的 import 或副作用
   - **Missing tests** —— 行为未锁定、回归覆盖薄弱、边界情况缺口
   - **UI/design defaults** —— 让 AI 界面显得未经审视的通用视觉模式

### UI/设计评审清单

这些是评审提示，不是绝对禁令。有明确理由的品牌、可访问性、信息密度或 design-system 选择予以保留。需要专门的视觉/设计评审时，委派 `omd-agent-designer`。

- **CJK 可读性**：正文 11-12px 要标记；中日韩正文一般至少需要 14px，除非有经过验证的高密度数据场景豁免。
- **阴影克制**：质疑每个表面、logo、背景、卡片、图标上的 box shadow；只在能阐明层级或交互的地方保留阴影。
- **内容层级**：标题已承载信息时，删掉重复的 eyebrow/标题/描述/多余 `<p>` 堆砌；通用 emoji 徽章除非属于产品语调，否则避免。
- **配色理由**：挑战默认的 AI 蓝紫配色（尤其 Tailwind 风的 `#3B82F6`），除非存在品牌或系统层面的理由。
- **布局节奏**：避免过分完美的 3/4 列均分网格——当产品语境更需要节奏、强调、不对称、carousel/bento 处理或卡片轻重变化时。
- **渐变克制**：收敛极端渐变，除非品牌刻意拥有那种视觉语言。

4. **一次只跑一个聚焦坏味道的 pass**
   - **Pass 1：删死代码**
   - **Pass 2：去重复**
   - **Pass 3：命名与错误处理清理**
   - **Pass 4：测试加固**
   - 每个 pass 之后重跑针对性验证。
   - 不把无关重构捆进同一批编辑。

5. **跑质量门禁**
   - 回归测试保持绿。
   - 对触及区域跑相应的 lint、typecheck、单元/集成测试（本宿主经 `pwsh`）。
   - 有现成的静态或安全检查就跑。
   - 门禁失败：修掉问题或回退有风险的清理，不强行闯关。

6. **用证据密集的报告收尾**
   必须报告：
   - **改动文件**
   - **化简点**
   - **行为锁定 / 验证运行**
   - **残留风险**

## 用法

- 加载 `ai-slop-cleaner` 技能并给出目标：`<target>`
- 只评审复查：`<target> --review`
- 限定文件清单：`<file-a> <file-b> <file-c>`
- 来自 ralph：只对 ralph 会话的改动文件跑 cleaner，然后回到 ralph 做清理后回归验证

## 适配判断

**合适：** `deslop this module: too many wrappers, duplicate helpers, and dead code`

**合适：** `cleanup the AI slop in src/auth and tighten boundaries without changing behavior`

**不合适：** `refactor auth to support SSO`

**不合适：** `clean up formatting`

## 状态契约

ai-slop-cleaner **不持模式状态**。它不做 `state_write`/`state_clear`，不在 `.omd/` 下创建文件；交付物是清理计划、被编辑的文件和证据密集的报告。在外层模式内被调用时（ralph 评审后清理、team-fix 阶段），持久化由外层模式的状态契约管辖。

# minimal-code-discipline（最小代码纪律）

在规划和编写代码改动时应用本技能的最小代码（YAGNI 阶梯）纪律。它让 diff 保持小巧且显然正确，同时不牺牲保护用户的检查。

本技能与 `ai-slop-cleaner` 互补：那个在残渣落地后清理，这个在残渣被写出来之前拦住它。

## 何时使用

- 用户要求最小、精简、YAGNI、最小可能的 diff
- 计划或进行中的改动正在膨胀，超出 stated request
- 写新代码，且容易出现 scope creep、重造 helper、投机性泛化
- 实现之前评审 proposed diff 的体量

## 何时不用

- 用户明确要求宽泛、功能丰富、面向未来的构建（用户的显式范围优先）
- 任务是用户标注为用完即弃的探索性脚手架
- 最小化压力会触及受保护行为（见"底线项"）

## 纪律

**先问存在性。** 先问这个改动是否需要存在；只为投机性未来需求服务的工作直接跳过。

**复用优先于新写。** 写任何新东西之前，先搜代码库（`grep`/`glob`）里是否已有 helper、类型或模式。绝不复制几个文件之外就存在的 helper——复用它，或把它提炼到一个共享位置。

**依赖阶梯。** 先找标准库，再找平台原生能力，再找已安装的依赖。手写代码是最后手段。几行代码能搞定就不要引入新依赖，除非用户显式要求或批准。

**先理解再最小化。** 先读受影响代码、跟随其执行路径。理解问题之后再交付最短正确 diff——你不写的代码永远不会出 bug。

**无聊优于聪明。** 宁可要无聊但显然正确的代码，不要聪明的代码。

**标出天花板。** 有意的简化用一行短注释记录：写清接受的限度，以及什么条件出现时就该换掉它。

**修根因，不修症状。** 在所有调用方共享的根因处修 bug，而不是每报一个症状打一块补丁。

## 底线项

绝不许被最小化掉的东西：
- 跨越信任边界的每一处校验
- 防数据丢失的错误处理
- 安全控制
- 可访问性基础
- 用户显式要求的范围

## 验证

报告完成之前确认：
- 每一行新增都值回票价（无投机性泛化、无重复 helper）
- diff 是正确解决所述问题的最短一个
- 底线项完好
- 测试仍通过，除用户要求外行为不变

## 状态契约

minimal-code-discipline **不持模式状态**。它是写作期纪律，不是执行模式：不做 `state_write`/`state_clear`，不在 `.omd/` 下创建文件。在外层模式（autopilot、ralph、team）内应用时，持久化由外层模式的状态契约管辖。

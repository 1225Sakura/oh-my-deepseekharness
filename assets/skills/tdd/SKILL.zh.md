# tdd（测试先行）

小步红绿，接缝先行约定。在 `launch` 运行中，接缝清单即已批准的规格/ticket 产物；在 `team` 运行中，执行队员自阶段交接文档继承。其余场景，在第一个测试存在之前与用户约定接缝——没人批准过的接缝，不写测试。

## 循环

一个测试 → 一份实现 → 重复：

1. 在某个接缝上写下下一个测试。运行它。看着它因你预期的原因失败——不可能失败的测试不是测试。
2. 实现让它变绿的最小改动。
3. 重复。每个测试都是曳光弹：穿过行为的一条窄而完整的路径，不是逐层孤立完工。

## 规则

- 期望值来自独立的事实来源——规格行、算例、有记录的输出。绝不来自被测实现本身：断言「代码恰好这么做了」的测试是镜子，不是检查。
- 替换只发生在接缝声明的边界类上——in-process / 本地可替换 / 自有远端端口 / 真外部，以接缝清单记录为准。测试正在行使的边界内部不放替身。
- 重构不属于本循环。它属于评审阶段（`review` / `ai-slop-cleaner`），归 fix 循环所有。红绿中途不重构。
- 修 bug 从复现它的失败测试开始——先复现后理论，调试者的铁律。
- 提议接缝时，用一行说清它拦住什么、放过什么——没人能定价的接缝选择是猜测，不是决策。

## 没有接缝可用时

如果行为无法在任何已批准接缝上测试，停下并明说：把缺失的接缝作为发现上报（喂给 `trace`/`analyze` 证据与环境适配审查），而不是发明接缝或穿透内部测。

## 产出

- 实际使用的接缝清单：边界类 + 每条接缝的拦住/放过一行
- 红绿证据——失败运行与通过运行（粘贴新鲜命令输出，不凭记忆）
- 接缝缺失发现（如有）
